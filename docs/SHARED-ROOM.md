# 共用房間與模式切換

正式 Firebase 多人模式以一場派對為單位：只建立一個房間碼，選邊站與 12 幕冒險共用玩家 UID、暱稱及座位。角色以房間碼與 UID 決定，切換時不變。兩種玩法的分數與進度分開保留。

主持登入後的「主持模式」會切換整場。確認後，原模式暫停，倒數保留剩餘時間；玩家入口及直播展示自動換到目標模式。玩家不用再次加入，邀請連結及 QR Code 不因模式而改變。未送出的表單草稿不會跨模式搬移。

結束房間會結束整場；清理會清除兩種模式的房間資料。清理後重新建立才產生新碼。冒險模式中途才加入的新玩家仍遵循既有觀戰規則，不會因切換模式獲得復活。

## 舊房間轉換

更新後，指定主持人首次登入會自動轉換舊資料。優先沿用目前展示模式的房間碼；若該模式沒有房間，使用另一個現有房間。合併兩邊玩家 UID，處理座位碰撞，保留兩邊遊戲進度。若總人數超過 20 位則拒絕轉換並恢復原狀，不默默刪除玩家。兩個舊匿名 UID 不會僅因暱稱相同而被視為同一人。

玩家共用原本 `viewer` Firebase App 的登入身分；沒有該登入身分的瀏覽器可沿用舊 `story-player` 身分。已開啟的舊網頁須重新整理一次，載入新版同步邏輯。

## 一致性與權限

- `room/public/broadcast` 儲存版本、房間碼、目前模式、修訂號及切換租約；不放私密答案。
- 主持人先取得切換租約，再以交易凍結兩個模式的加入、作答及聊天入口。只有目前模式可以執行遊戲指令。
- 目標玩家名單、狀態與模式指標以一次 Firebase 多路徑更新提交；玩家只在提交後換頁。
- 不覆蓋原模式暫停後的資料，也不以舊快照覆蓋短答分享同意，避免遺失同步中的撤回。
- 失敗時嘗試恢復原有活動模式；斷線時保留可恢復的暫停快照。租約一分鐘到期後，重新整理主持頁可恢復未完成切換。
- 使用現有指定主持人權限，無須擴大資料庫讀寫規則。玩家仍不能讀取其他人的答案、私密短答或主持資料。
- `?demo=1` 保留原本各模式本機試玩工具；正式多人同步以 Firebase 模式驗證。

## 驗證

`npm test` 包含共用碼、20 人多次切換、角色保持、倒數暫停恢復、舊房間轉換、玩家移除、觀戰規則與固定邀請網址。

`npm run test:rules` 包含真實 Firebase 模擬器上的跨模式名單及私密信箱存取、拒絕非主持切換、並行切換、整場清理及租約恢復。

瀏覽器以本機 Auth/Database 模擬器驗證主持登入、玩家加入一次、選邊站 → 冒險 → 選邊站、直播展示同步和玩家重新整理後仍留在房間。
