# 選邊站：輪流猜主角

## 正式玩法

- 新房間採「輪流猜主角」，主持入口仍是 `host.html` →「選邊站」。
- 預設每回合 10 題、共 3 回合，合計 30 題。主持開場前可設定每回合 1–30 題、全場 1–3 回合；開始後固定設定，以免不同裝置對進度理解不同。
- 每題換一位主角，按實際入座時間、座位順序輪換，跨回合繼續輪流。遲到者加入輪替隊尾，已移除的 UID 跳過；同座位的新身分不繼承舊紀錄。
- 主角只填自己的選擇；其他人一起提交自己的選擇及猜主角的答案。揭曉前，只有本人及正式主持可讀取私人答案。
- 主持揭曉後公開主角選項及大家的個人選擇；猜中主角加 1 分。主角不猜自己，不取得公開猜題分數。沒有有效答案的主角，該題所有人不計分、也不增加默契。
- 默契只比較各玩家自己的答案與當題主角答案，不比較猜測，也不累積兩個非主角之間的默契。共同至少 2 題、相同率至少 70% 才符合靠攏條件。
- 主持專用隱藏分：每位有效猜題者猜中，主角「被猜中」加 1；猜錯，主角「未被猜中」加 1。漏答不扣分、不算猜錯。兩種分數分開，重複揭曉不重算。
- 完成設定題數或主持提前結束時，公開猜題總分最高且至少 1 分的在座玩家獲封「心水清大師」；同分並列，全部 0 分不硬選得主。
- 最後一題揭曉後保留聊天時間、鎖定新入座及出題。主持可結束房間，再清理資料開新場。

30 道四選一題目包含人生選擇、興趣、品味及生活習慣。主持仍能自由選題，揭曉後預選尚未用過的題目；如果設定超過 30 題，可以重用題目。題目不判定人格、不做心理診斷。

## 資料與相容性

- `/room/public/state`：`ruleset: spotlight-v1`、題數／回合設定、當題主角 UID／名稱、目前回合與題序、完成狀態。
- `/room/public/rotation/order`：輪替 UID 順序。每次開始以房間層級交易驗證現有房間碼及題號。
- `/room/answers/{round}/{uid}`：原有私人答案；主角 `prediction: -1` 表示不猜自己，觀眾仍需 0–3。規則依可信的公開主角 UID 驗證，不依賴隱藏按鈕。
- `/room/hostOnly/spotlight`：已結算題號與各主角 `turns / guessed / unguessed / missed`；僅正式指定主持可讀寫。
- `/room/hostOnly/affinity`：私人兩人默契；公開島民位置僅在揭曉更新。
- `/room/public/results`：揭曉後的主角選擇、公開票數、個人選擇與得分；不包含原始猜測。
- `/room/public/awards`：稱號、最高分與得主 UID。

隱藏分的原始欄位不傳給玩家或 OBS；由於猜題得分和主角身份公開，熟悉規則者仍可能推算部分統計，不能將「介面不展示」理解為不可推算。主持可能同時是玩家，正式主持權限本身能讀取私人答案；這是可信主持架構的限制。

舊房間不在活動中途改規則：沒有 `ruleset` 的房間仍用猜多數玩法。舊場結束後保留或備份所需紀錄，清理，再建立新房間，即啟用新版。12 幕冒險的玩法與資料不變。

## 本機試玩

開啟 `http://127.0.0.1/hoho-events/dist/host.html?demo=1`，建立房間，按「加入三位示範玩家」。開啟「我要一起玩」可用自己的暱稱加入。開始一題後，自己的答案需手動提交；「補齊示範玩家答案」只補示範帳號未交的答案。截止、揭曉後可繼續下一位主角。

此功能只在明確的本機模擬模式出現；正式主持頁沒有示範玩家或自動填答。新模擬存檔 `hoho-spotlight-demo-v1` 與舊模擬 `hoho-demo-v1` 分開，舊存檔不刪除。模擬版只同步同瀏覽器分頁，不代表跨裝置多人。

## 規則發布順序

1. 等目前活動結束，在 Firebase Realtime Database → 規則，備份現有規則。
2. 貼上 GitHub 備份分支 `database.rules.json` 的完整 Raw 內容，按「發布」。這次只更新原房間答案中主角免猜的驗證；不變更主持 UID、登入方式、密碼或費用方案。
3. 網站部署完成後重新整理主持頁；完成舊房間清理後建立新場。
4. 規則未更新時，主角的 `prediction: -1` 會被拒絕，所以不能先發布網站再補規則。

規則完整重建命令：
```
node scripts/generate-rules.js
node scripts/add-story-rules.mjs
node scripts/add-voyage-rules.mjs
```

依據 Firebase 官方[交易與寫入文件](https://firebase.google.com/docs/database/web/read-and-write)及[規則繼承文件](https://firebase.google.com/docs/database/security/core-syntax)，使用房間層級原子交易結算，私人分數放在公開讀取節點之外。
